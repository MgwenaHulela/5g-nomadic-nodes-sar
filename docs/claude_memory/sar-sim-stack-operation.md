MSc SAR simulation (UCT, 2026): Gazebo Harmonic + OAI 5G RAN (rfsim) + Open5GS. Single entrypoint is `./start_full_stack.sh` — it owns Gazebo exclusively (kills any stray `gz sim` first; never hand-start Gazebo: a hand-started server lacks GZ_SIM_RESOURCE_PATH and the robot includes fail). Since 2026-07-10 all three robots (`sar_uav` static x500 at 40m, `sar_ground_alpha`/`bravo` static turtlebot3_burger at 15m/30m) are **includes in worlds/sar_open_field.sdf**, NOT runtime spawns — Harmonic's SceneBroadcaster drops merge-included EntityFactory spawns from the scene graph, making them invisible to any GUI (physics/pose still work). All static: motion is set_pose teleports only; non-static burgers creep ~0.5m/min (overnight alpha drifted 780m and crashed its UE). GUI: `./view_gui.sh`; `/marker` is a SERVICE (GUI MarkerManager), not a topic — gazebo_viz sends markers via node.request; the metrics panel is TopicEcho on /sar/metrics (TopicViewer only lists names).

**Why:** channel_bridge.py and scripts/gazebo_viz.py key on those exact model names; two Gazebo instances or wrong names silently freeze the channel pipeline.

**CRITICAL (2026-07-11): OAI's channelmod `path_loss_dB` is a GAIN, not a loss** — apply_channelmod.c applies pow(10, +x/20); positive values amplify until sample clipping. The bridge keeps ploss as a positive attenuation magnitude internally and negates once at the telnet send. Recalibrated world: noise_power_dB −40 (was −6; at −6 a unity signal has ~6dB SNR and can't attach), startup config ploss 0 (initial access fails at −13; bridge applies baselines post-attach), baselines UL 8/13 DL 3/8, TCP halves ~20dB attenuation, link dies ~35dB, safe cliff 30dB, TX_REF −42 (measured SS-RSRP = −42 − DL attenuation, verified 1:1). UE SS-RSRP is a genuine observable AFTER this fix; all pre-fix datasets (2026-07-10/11 campaigns) and the paper's dB numbers reflect the inverted regime.

**How to apply:**
- Since 2026-07-09 the UE TUNs are moved into per-robot netns (`robot_alpha`/`robot_bravo`, scripts/setup_robot_netns.sh, runs as final step of start_full_stack.sh) so BOTH directions cross the air. Uplink tests: `sudo ip netns exec robot_alpha iperf3/ping ...`; downlink/C2: plain `ping 10.45.0.2` from root ns. `ping -I oaitun_ue1 ...` in the root ns no longer works (interface lives in the netns). Before netns, host->UE traffic short-circuited via loopback (UE IPs were host-local) — any historical DL/`--reverse`/UDP-reverse numbers are loopback artifacts.
- Verify integration end-to-end: teleport a robot via `gz service .../set_pose`, watch `/tmp/ch_bridge.log` for `-> ploss` lines tracking distance, then over-air ping (see netns commands above). Expected mapping (2026-07-09): 10m→~14dB, 50m→~17dB, 100m→~31dB, 150m→~38dB (alpha UL, baseline 20). Verify traffic is really on the air via `~/openairinterface5g/nrMAC_stats.log` (live per-UE dlsch/ulsch goodput; RNTIs rotate after RLF).
- **45dB absolute ploss = documented RLF cliff** (RNTI churn, BLER 0.86 — commit fc3ef41). Bravo UL baseline 25 hits it around ~160m+. High RTT (up to ~1s) at 150m is normal HARQ behavior, not failure. After a large teleport, give the EMA ~15-20s before judging link health.
- Negative deltas (robot closer than 50m ref) are intentionally allowed since 2026-07-09 (floored at PLOSS_MIN=10); re-clamping them to 0 recreates a <50m dead zone that poisons the ML training CSVs.
- Harness quirk: `pkill -f "gz sim"` (or channel_bridge.py / gazebo_viz.py) inside a Claude Bash call kills the wrapper shell itself because the pattern appears in its own cmdline. Use bracket patterns (`"gz [s]im"`) and put kill and relaunch in separate Bash calls; launch long-runners with `setsid nohup ... < /dev/null &`. Same self-match trap applies to pgrep inside Monitor scripts that also contain a launch line — track long runs by PID file (single pid via `pgrep ... | head -1`), not by name.
- OAI logs grow ~5GB/h (gnb) + ~2GB/h per UE: an unattended night hit 272GB and filled the disk, crashing bridge+patrol. scripts/log_janitor.sh (launched by start_full_stack) truncates them at 5GB real usage. NEVER truncate a live log and then let tail_file read it naively: the file goes sparse (writer keeps its offset) and readline() inflating the hole OOM-killed two patrols at 14.7GB RSS — metrics_collector.tail_file now caps backlog at 4MB.
- channel_bridge (since 2026-07-12) verifies its telnet links at startup: probe-until-live + write/read-back of every model baseline; OAI telnet accepts ONE client per port (extra sockets sit unaccepted in the backlog swallowing writes silently — this hid bravo's never-modulated UL for the project's entire history). One shared TelnetLink per port.
- TurtleBots creep ~0.5m/min when idle (dynamic burgers; since 2026-07-10 they DRIVE via gz-sim DiffDrive in models/sar_burger — auto_patrol --free publishes cmd_vel with pose feedback; other modes still teleport).
- Dataset caveat: patrol_20260710_131330.csv (90-min run) has ~19% samples with tcp=0 on a live link — iperf server-busy cascade, fixed in auto_patrol (retry + settle gaps) same day. Salvage filter: drop rows where tcp==0 AND ping_loss==0. Analysis tooling: scripts/analyze_patrol.py (report + 4 figures per run).
- Coverage edges (measured 2026-07-10): alpha dies ~135m, bravo ~130m at h=40; RLF is sticky — the UE may never re-attach without restart_ran.sh. --max-radius=110 keeps 90-min runs outage-free. Edge moves with altitude: safe_radius() in auto_patrol gives 86m@20m / 117m@40m / 149m@60m.
- Nomadic mode (2026-07-11): `--vary-uav` flies the UAV through a 9-waypoint x/y/z schedule; robots' annulus recenters on the UAV and follows safe_radius(alt); an emergency teleport guard rescues robots stranded by UAV hops (without it both UEs die sticky-RLF). Flagship dataset: patrol_20260711_020453.csv — 530 samples/robot, 3h, z 20–60m, 0 outages/artifacts, model parity MAE 0.5–0.6dB.
